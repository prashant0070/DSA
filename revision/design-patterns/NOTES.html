SDET

Design patterns

Recurring solutions. In interviews: framework design, and Java OOP. Talk problem → structure → trade-off → SDET example.

Creational

Factory Hide construction. Test asks for Chrome; factory returns a configured driver. Do not scatter new ChromeDriver().
Builder Many optional fields: baseUrl, headless, timeout. Fluent, validated at build.
Singleton One instance. OK for immutable config. Bad for WebDriver in parallel tests.
flowchart LR
  Test --> Factory["DriverFactory.create"]
  Factory --> Chrome
  Factory --> Firefox

Structural

Decorator Wrap same interface: logging, screenshot, retry around WebDriver.
Facade One method hides a messy flow: checkout as guest.
Adapter Wrap a legacy client to your interface during Selenium → Playwright migration.
flowchart LR
  Test --> LogDec["LoggingDriver"]
  LogDec --> Shot["ScreenshotDriver"]
  Shot --> Real["ChromeDriver"]

Behavioral

Strategy Swap algorithm: wait policy, retry, browser. Number one pattern in test frameworks. Also Comparator in heaps.
Template Method BaseTest setup/teardown; subclass fills the varying step. Keep the base thin.
Observer Listeners on pass/fail: Allure, screenshots.

Test architecture (not GoF)

POM: one class per page. Page Component Model: header/modal as pieces. DI: inject driver and config — never static driver.

  Test --> LoginPage
  LoginPage --> Driver
  Test --> Config
